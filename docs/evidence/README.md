# Read-only design evidence

Generated by `python3 tools/profile_inputs.py`, using only the Python standard library. Original files remain unchanged. These JSON artifacts support design review; they are not generated application reports or a substitute for the PostgreSQL submission.

| File | Contents |
| --- | --- |
| [input-profile.json](input-profile.json) | All five original file hashes/sizes, row counts, config counts, payment population totals, settlement amount total |
| [mapping-before-probe.json](mapping-before-probe.json) | Original config diagnostic summary, key counts, unmatched keys, duplicate-selector diagnostics, rule controls with every contributing source line, first 20 group/bucket variances and full variance count |
| [mapping-after-probe.json](mapping-after-probe.json) | Candidate config edits applied in memory, same scope/normalization, independently calculated source buckets, key/variance checks and rule controls |

The original duplicate selectors use disclosed all-candidate diagnostic semantics, with a scoped Transfer description normalization. The after probe removes payment rules at original lines 5 and 72, updates payment line 14, and updates settlement lines 61, 63, 95 and 118. These line-based edits are confined to the research probe: production fixes must be guarded SQL against rule identities and old values, not Go branches.

`group_bucket_variance_count` counts `(shared key, summary bucket)` differences, not raw rows or distinct keys. It changes from 5,973 to 0. `rule_controls.source_lines` contains every nonzero contributing source line for that rule. Exact raw amounts and selectors are recoverable from immutable input hashes and those lines. Before variance samples are intentionally limited to 20; the full variance count is computed before sampling. Regenerate the probe or use the implemented explain command for a full audit export.

## Scope of this tool

The probe assumes the observed header positions, locale, source shapes and known template tokens; its amount parser is intentionally not a production validation parser. It is single-process in-memory analysis. It does not enforce PostgreSQL transaction/constraint semantics, validate arbitrary input schemas, generate XLSX, test SQL fixes, or guarantee performance. Production tests must implement the stricter contracts, not copy the probe as the application.

The worksheet was inspected separately for Summary labels/positions and Consolidated headers. The sample's data values were not used to calculate probe results. The PDF was read in full and rendered for visual review.
